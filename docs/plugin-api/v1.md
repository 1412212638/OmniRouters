# Task Plugin API v1

Task plugins are single-file synchronous ECMAScript modules. The host owns
HTTP connections, persistence, polling, retries, billing, settlement, and
refunds. Plugins transform requests and responses and report bounded usage
facts.

## Manifest

Every plugin exports `meta`, `buildSubmitRequest`, `parseSubmitResponse`, and
`parseTaskResult`. A `per_task` plugin also exports `buildQueryRequest`; a
`batch` plugin exports `buildBatchQueryRequest` and `parseBatchResult`.

```js
export const meta = {
  apiVersion: 1,
  key: "vendor",
  name: "Vendor",
  version: "1.0.0",
  author: {name: "Author"},
  models: ["vendor-model"],
  fetchMode: "per_task",
};
```

`meta.routes` may register authenticated vendor-native routes. `meta.protocols`
may claim host-owned `openai_responses` or `openai_video` bindings. Route and
protocol conflicts are checked by the host before an enabled plugin is
published. `routes[].models` narrows a submit or dynamic route to declared
models; query routes do not accept that field.

The host validates metadata, required exports, route ownership, allowed hosts,
and protocol mode support before saving an enabled version. Uploading a plugin
is an administrator-level trust decision equivalent to configuring a channel.

## Hooks

`buildSubmitRequest(ctx)` and `buildQueryRequest(ctx)` return a request
descriptor. The descriptor may contain a JSON body, a multipart parts list, or
an explicitly credentialless GET/HEAD request. The host performs the HTTP
request and validates the destination against the channel base URL and
`meta.allowedHosts`.

`parseSubmitResponse(ctx, response)` returns `{taskId, taskData?, immediate?,
state?}`. `parseTaskResult(ctx, body, response)` returns a normalized result.
Batch parsing returns an array of normalized results with a `taskId`.

Usage hooks may return facts such as seconds, resolution, upstream units, or
counts. They must not calculate prices or alter quota. The host validates and
clamps billing inputs before pre-consume and settlement.

## Query context

Polling hooks receive `TaskQueryContext`, rebuilt from the persisted task row:

| Field | Meaning |
|-------|---------|
| `taskId` | Upstream task id, falling back to the gateway task id |
| `publicTaskId` | Gateway task id |
| `action` | Persisted task action |
| `model` | Original client model |
| `upstreamModel` | Mapped upstream model, falling back to `model` |
| `baseUrl`, `apiKey`, `authHeader`, `auth` | Channel credentials |
| `data` | Latest persisted upstream response snapshot |
| `state` | Plugin-owned persisted state |

There is no query-side `requestBody`. Values needed by later polling rounds
must be saved in `state` at submission time. `Task.Data` is replaced by each
valid poll result, while `state` is replaced only when a hook explicitly
returns it. Persisted plugin state is limited to 1 MiB and is never exposed in
public task views.

`parseTaskResult` and `parseBatchResult` receive a third response argument:
`{status, headers}`. Batch request and parse hooks receive the full
`tasks: TaskQueryContext[]` collection, including per-task state and model
identity.

## Polling and failures

Plugins must return `UNKNOWN` for a response shape or provider status they do
not recognize. They must not fall back to `IN_PROGRESS`, because that can keep
a task pending while holding pre-consumed quota indefinitely.

The host classifies HTTP responses before trusting a non-terminal result:

| Response | Host behavior |
|----------|---------------|
| 2xx | Invoke the parse hook |
| 404 / 410 | Fail immediately and run the existing refund path |
| 401 / 403 | Keep the task status, count a poll failure, and warn; do not disable the channel |
| 429 / 5xx / transport error | Count a poll failure |
| Other 4xx | Expose the status to the hook; a non-terminal result counts as unrecognized |

Valid 2xx non-terminal results reset the consecutive failure count. After
`TASK_POLL_MAX_FAILURES` failures (default 20), the host transitions the task
to `FAILURE` through the existing CAS-protected update and settlement/refund
chain. The `TASK_TIMEOUT_MINUTES` sweep remains the outer deadline. A failed
task whose refund could not be funded remains marked for reconciliation.

## Files and artifacts

Multipart files enter JavaScript only as opaque `FileReference` values. JSON
file placeholders are resolved by the host after the hook returns, and the
host enforces per-file and total size limits.

Plugins that expose outputs may export `listArtifacts(task)` and
`buildContentRequest(ctx)`. Artifact content is served through host-controlled
capability URLs; provider URLs and private task identifiers are not exposed as
public capabilities without the host checks.

## Security

Plugins have no `fetch`, filesystem, `require`, imports, async functions, or
environment access. The host controls execution time, concurrency, request
size, destination validation, authentication, and persistence. Enable
`DEBUG=true` only when needed for diagnosis and never log credentials, request
bodies, upstream payloads, or private URLs from plugin code.

Use the local CLI to validate a plugin and replay deterministic fixtures:

```sh
new-api plugin lint plugin.js
new-api plugin test plugin.js --fixture golden.json
```
