# 实名认证方案（暂定）

状态：已开始实施第一版；个人和企业接口已验证。

## 1. 目标与范围

第一版支持两类核验，用户在未认证时二选一：个人用户的姓名和身份证号二要素核验，或企业的统一社会信用代码、企业名称、法人/主要人员姓名和身份证号四要素核验。用户提交对应信息，由 OmniRouters 服务端调用对应阿里云市场接口；只有所有必要字段匹配时，才将用户标记为已认证。

一个用户只允许存在一种已生效的认证类型。认证成功后锁定认证类型和认证资料，用户不能再次切换认证方式或修改已认证信息。

第一版不做微信/支付宝扫码、人脸识别和活体检测。用户协议负责说明实名信息的使用和保存规则，不在提交页面增加单独的协议勾选流程。

## 2. 上游接口

服务商：阿里云市场“身份证二要素核验”接口。

接口：

```text
POST https://zidv2.market.alicloudapi.com/idcheck/Post
```

请求 Header：

```text
Authorization: APPCODE <AppCode>
Content-Type: application/x-www-form-urlencoded
```

请求体：

```text
cardNo=<身份证号>&realName=<姓名>
```

请求体中的姓名需要按 `application/x-www-form-urlencoded` 规则编码。姓名和身份证号只由后端发送给上游；浏览器不直接访问阿里云接口，也不把 AppCode 暴露给用户。使用 POST 请求可以避免证件信息出现在上游 URL 查询参数中。

### 2.1 业务结果判定

接口返回的 `error_code` 表示接口通信结果，`result.isok` 表示身份核验结果。`error_code = 0` 只代表接口调用成功，不能单独当作实名认证成功。

业务结果只有两种：

| `result.isok` | 含义 | 实名状态 |
| :---: | --- | --- |
| `true` | 姓名和身份证号匹配 | 认证成功 |
| `false` | 姓名和身份证号不匹配 | 核验失败 |

认证成功的严格条件：

```text
HTTP 状态 = 200
且响应 error_code = 0
且 result.isok = true
```

`error_code = 0` 且 `result.isok = false` 是“接口调用成功、身份信息不匹配”，应作为核验失败处理，不应当作为系统异常。

### 2.2 接口验证结果

2026-11-01 已使用临时 AppCode 和测试身份信息完成一次真实请求，结果如下：

- 请求方式：POST 表单请求；
- HTTP 状态：`200`；
- `error_code`：`0`；
- `result.isok`：`true`；
- 上游返回了脱敏身份字段和流水号。

因此，当前服务商的地址、AppCode Header、表单字段名 `cardNo`/`realName` 以及成功判定规则均已验证可用。测试凭据和测试身份信息不写入文档、代码或日志；该请求会计入服务商调用额度。

### 2.3 上游错误码

服务商明确提供的返回码包括：

| `error_code` / HTTP 状态 | 含义 | 系统处理 |
| ---: | --- | --- |
| `0` / `200` | 请求成功 | 再按 `result.isok` 判定 |
| `10028` / `400` | 缺少参数或参数错误 | 返回用户输入错误，不改变认证状态 |
| HTTP `403` | AppCode 无效、调用次数用尽等网关拒绝 | 分别提示配置错误或额度用尽，不改变认证状态 |
| 其他非零业务码或非 2xx HTTP 状态 | 服务商、第三方或接口异常 | 返回服务暂不可用，不改变认证状态 |

服务商说明调用次数只对 HTTP `200-300` 响应扣减，因此后端不能为了重试而篡改或吞掉上游状态。后端需要同时读取 HTTP 状态和 JSON `error_code`，不能只判断 HTTP 状态或只判断响应是否可解析。

### 2.4 企业认证接口

服务商：阿里云市场“企业工商信息四要素核验”接口。

接口：

```text
POST https://qysysjk.market.alicloudapi.com/government/safety/9151
```

认证 Header：

```text
Authorization: APPCODE <AppCode>
```

请求参数由接口文档定义为查询参数，虽然请求方法是 POST：

```text
key=<服务商购买的 API key>
registration_number=<统一社会信用代码或工商注册号>
ent_name=<企业名称>
name=<法人/主要人员姓名>
idcard=<法人/主要人员身份证号>
```

后端应使用 URL 编码构造 POST 请求，并避免在日志中记录完整 URL。若服务商后续提供 POST body 版本，应优先切换到 body 传参。

注意：当前资料存在不一致：参数表把 `key` 标记为必填，但示例 curl 没有传 `key`，只传了 AppCode。实现前必须用服务商测试请求确认 `key` 是否真的必需；如果必需，后台要单独保存企业接口 key，不能让用户填写。

### 2.5 企业认证结果判定

企业接口的 `code` 只表示查询接口是否成功，四个 `*_result` 字段分别表示各项信息是否匹配：

| 字段 | `1` | `2` |
| --- | --- | --- |
| `ent_name_result` | 企业名称一致 | 企业名称不一致 |
| `registration_number_result` | 统一社会信用代码/工商注册号一致 | 不一致 |
| `name_result` | 法人/主要人员姓名一致 | 不一致 |
| `idcard_result` | 法人/主要人员身份证号一致 | 不一致 |

企业认证成功的严格条件：

```text
HTTP 状态为 2xx
且响应 code = "10000"
且 ent_name_result = "1"
且 registration_number_result = "1"
且 name_result = "1"
且 idcard_result = "1"
```

任意一个字段为 `2` 都是核验失败；字段为 `3` 或缺失属于异常，不得标记认证成功。

服务商错误码处理：

| `code` | 含义 | 系统处理 |
| ---: | --- | --- |
| `10000` | 查询成功 | 再按四个 `*_result` 字段判定 |
| `10001` | 查询无结果 | 核验失败，不改变认证状态 |
| `10002` | 信息不全 | 返回输入错误，不改变认证状态 |
| `10003` | 报文格式错误 | 返回输入错误，不改变认证状态 |
| `10004` | 系统错误 | 返回服务暂不可用，不改变认证状态 |
| `10005` | 查询参数错误 | 返回输入错误，不改变认证状态 |

响应中的 `seqNo` 是每次调用的唯一流水号。认证记录可以保存它，便于管理员联系服务商排查，但不能把完整请求参数或身份证信息写入审计日志。

### 2.6 企业接口验证结果

2026-11-01 已使用临时 AppCode 和测试企业信息完成一次真实请求，且未携带参数表中标记的 `key` 字段，结果如下：

- 请求方式：POST，四个业务字段通过查询参数传递；
- HTTP 状态：`200`；
- `code`：`10000`；
- `name_result`：`1`；
- `idcard_result`：`1`；
- `ent_name_result`：`1`；
- `registration_number_result`：`1`；
- 返回了 `seqNo` 流水号。

因此，当前服务商的企业接口地址、AppCode Header、四个参数名称和四要素成功判定规则均已验证可用。此次测试未携带 `key` 也成功，暂不把 `key` 作为运行时必需配置；仍保留文档冲突记录，后续以服务商正式说明为准。测试凭据和测试身份/企业信息不写入文档、代码或日志；该请求会计入服务商调用额度。

## 3. 后台配置

在管理员系统设置的安全区域增加“实名认证”配置，至少包括：

默认前端位置：`系统设置 → 身份验证 → 实名认证`。运行时配置键为：

```text
real_name_verification.enabled
real_name_verification.enforcement_enabled
real_name_verification.personal_enabled
real_name_verification.personal_app_code
real_name_verification.enterprise_enabled
real_name_verification.enterprise_app_code
```

`personal_app_code_configured` 和 `enterprise_app_code_configured` 只读返回配置状态，不接受管理员直接修改。证件加密密钥通过环境变量 `REAL_NAME_ENCRYPTION_KEY` 提供。

### 3.1 实名认证功能开关

`实名认证功能` 默认关闭。

- 关闭：用户看不到认证入口，系统不调用上游。
- 开启：用户可以在个人资料中主动提交实名认证。

这个开关只控制实名认证功能是否可用，不影响用户创建 API Key 的权限。

### 3.2 强制实名认证服务访问开关

`未完成实名认证时禁用模型/API 服务` 默认关闭。

- 关闭：用户可以实名，也可以不实名；Key 创建和模型/API 服务访问保持现状。
- 开启：用户没有完成个人认证或企业认证中的任意一种时，除登录、个人资料、实名认证、帮助和必要的账户恢复入口外，所有平台业务服务均不可用，包括模型/API、订阅、充值和发票等；已有 Key 发起的请求也不可用，同时不允许创建普通 Key、订阅 Key，也不生成注册初始模型 Key。
- 用户完成个人或企业任意一种认证后，平台业务服务恢复，Key 创建限制解除。

这是独立于“实名认证功能”开关的策略开关。开启策略开关时，如果实名认证功能没有开启，或没有任何一个认证方式可用，后台应提示配置冲突，不能让管理员保存一个无法完成认证的配置。登录、个人资料、实名认证提交与查询、帮助和必要的账户恢复入口仍需可访问，避免用户因服务访问受限而无法完成认证或联系管理员。

### 3.3 服务商认证配置

第一版推荐只实现 AppCode 调用方式：

- 个人认证服务地址：默认固定为 `https://zidv2.market.alicloudapi.com/idcheck/Post`；
- 企业认证服务地址：默认固定为 `https://qysysjk.market.alicloudapi.com/government/safety/9151`；
- 个人认证方式开关：独立控制个人认证是否可用；
- 企业认证方式开关：独立控制企业认证是否可用；
- 个人认证 AppCode：敏感配置，服务端保存，前端只显示“已配置”；
- 企业认证 AppCode：单独配置，敏感配置，服务端保存，前端只显示“已配置”；
- 企业接口 key：仅在服务商确认必需时配置，服务端保存，前端只显示“已配置”；
- 测试连接：使用管理员提供的测试信息时要谨慎，不能把测试证件或企业信息写入日志或持久化记录；测试请求也应计入上游额度提示。

每种认证方式只有在“方式开关开启且对应凭据已配置”时才算可用：

- 只启用并配置个人认证：用户只能选择个人认证；
- 只启用并配置企业认证：用户只能选择企业认证；
- 两种都启用并配置：用户可以二选一；
- 两种都不可用：用户不能提交认证，强制实名服务访问开关也不能开启。

方式开关只控制后续是否可以使用该服务商进行新认证，不回溯撤销已经成功的认证记录。若需要撤销已成功认证，必须使用管理员的“重置认证状态”操作。

阿里云页面同时提供 AppKey 和 AppSecret。它们属于另一套签名认证方式，第一版不使用，后台可以暂不展示；如果未来支持签名认证，再增加认证方式选择和签名算法实现。不能把 AppKey/AppSecret 直接当作普通 Header 发送。

## 4. 数据模型与保存策略

增加独立的实名认证记录表，避免把证件信息混入用户基础表。每个用户只保留一条当前认证记录，至少包括：

- 用户 ID；
- 认证类型：个人或企业，认证成功后不可由用户修改；
- 认证状态：未认证、已认证；
- 个人认证的加密姓名和完整身份证号；
- 企业认证的加密企业名称、统一社会信用代码/工商注册号、法人/主要人员姓名和身份证号；
- 脱敏展示字段（姓名、证件尾号、企业名称、统一社会信用代码尾号）；
- 服务商标识；
- 上游订单号或 `seqNo`；
- 最近认证时间；
- 创建时间和更新时间。

认证失败不保存本次提交的完整个人或企业信息。需要记录失败次数或最近失败原因时，只保存错误分类，不保存原始请求参数和完整上游响应。认证成功后，企业信息和个人信息一样作为用户实名资料保存，管理员可按权限查看。

### 4.1 加密

姓名和身份证号使用服务端专用加密密钥进行 AEAD 加密后落库，密钥不进入数据库、前端、仓库或日志。建议使用独立环境变量：

```env
REAL_NAME_ENCRYPTION_KEY=
```

密钥缺失时不允许提交认证，也不能回退到明文存储。未来如需轮换密钥，再增加版本字段和迁移流程。

## 5. 用户端流程

个人资料页新增“实名认证”区域，并提供“个人认证”和“企业认证”两个选项：

1. 功能关闭时不显示认证表单。
2. 未认证时只显示当前已启用且已配置的认证方式；两种都可用时用户选择个人认证或企业认证，选择后显示对应字段。
3. 个人认证按 `result.isok = true` 显示“已认证”；企业认证按四个 `*_result` 全为 `1` 显示“已认证”。
4. 个人 `result.isok = false`，或企业任一结果为 `2`，显示信息未通过核验，允许重新提交，也可以在认证成功前切换认证类型。
5. 个人上游 `10028/HTTP 400`、企业 `10002/10003/10005` 显示参数错误；HTTP `403` 根据响应区分 AppCode 无效和额度用尽；其他非 2xx、非零业务码或网络超时显示“认证服务暂时不可用”，允许稍后重试。
6. 认证成功后隐藏类型选择和编辑入口，锁定认证类型及全部认证资料；用户不能再次切换或修改。

用户侧接口永远不返回完整身份证号、统一社会信用代码或工商注册号。所有用户输入均由后端校验格式和长度，不能只依赖上游返回。

## 6. 管理员端流程

管理员用户详情中增加实名认证信息：

- 是否已认证；
- 认证时间；
- 认证类型、服务商和订单号/`seqNo`；
- 脱敏信息默认展示；
- 通过明确的“查看完整信息”操作查看个人姓名、身份证号，或企业名称、统一社会信用代码、法人/主要人员姓名和身份证号；
- 提供“重置认证状态”操作，使用户可以重新认证。

完整信息只在管理员权限通过后由后端返回，不放进普通用户列表接口。管理员可在特殊情况下重置已锁定的认证记录；重置操作必须填写原因，并写入安全审计日志，记录用户 ID、认证类型、操作者、动作、原因和时间，不记录完整证件号。重置后用户回到未认证状态，可以重新选择个人或企业认证。若强制实名服务访问开关开启，重置后所有模型/API 调用都会再次被拦截，包括现有 Key；创建 Key 也会被拦截。

## 7. API 设计（暂定）

用户接口：

```text
GET  /api/user/identity-verification
POST /api/user/identity-verification/individual
POST /api/user/identity-verification/enterprise
```

`GET` 返回当前认证类型、认证状态、对应的脱敏字段和认证时间，以及当前可用的认证方式列表。未认证用户只能调用已启用且已配置的对应 `POST` 接口；认证成功后，另一个认证接口应拒绝提交，避免绕过锁定规则。

管理员接口：

```text
GET  /api/user/:id/identity-verification
POST /api/user/:id/identity-verification/view
POST /api/user/:id/identity-verification/reset
```

管理员查看完整信息建议使用一次性、短时有效的安全证明，避免完整证件信息长期留在浏览器缓存中。重置接口应明确认证类型，避免误重置另一种认证记录。

## 8. 强制实名与服务访问

强制实名检查必须在服务端执行，不能只依赖前端隐藏按钮。除创建入口外，还必须覆盖所有需要登录的业务服务请求，使用户已有 Key 或登录态都不能绕过实名策略。可在统一鉴权/业务入口增加用户实名认证状态检查，并明确放行登录、个人资料、实名认证、帮助和必要的账户恢复入口。

需要限制的 Key 创建路径：

- 普通模型 API Key：`POST /api/token/`；
- 订阅套餐 API Key：`POST /api/subscription/self/:id/token`；
- 注册时自动生成的初始模型 API Key，不得生成可绕过策略的初始 Key。

当强制开关开启且用户未认证时，所有被限制的业务服务请求返回稳定的业务错误码和多语言提示，例如“请先完成实名认证后再使用服务”。Key 创建入口提示“请先完成实名认证后再创建 API Key”。

当前规则：个人认证或企业认证只能选择一种，任意一种成功即可满足“已实名”条件；认证成功后不能再切换认证类型。管理员可以在特殊情况下重置认证；重置后用户可重新选择认证类型。重置时必须记录操作原因并留审计记录。管理员重置不会删除或修改现有 Key，但在强制实名开关开启时，现有 Key 的模型/API 服务请求和新建 Key 都会被拒绝，直到用户重新完成任意一种认证。

开启强制实名服务访问开关时，如果用户仍未认证，不应生成初始模型 Key；注册完成后用户先完成实名认证，再创建 Key。开关开启期间已有 Key 保留，但不能调用模型/API 服务；用户完成认证后可继续使用。

系统访问令牌（个人资料里的管理访问令牌）与模型 API Key 用途不同，第一版不用于模型/API 服务调用，不纳入该服务访问限制。用户仍需能访问个人资料和实名认证流程。

## 9. 安全、隐私与日志

- 姓名、身份证号不写入普通请求日志、错误日志、审计详情、性能日志或上游地址记录。
- 上游使用 POST 表单体传参，后端 HTTP 客户端和错误处理仍必须避免记录完整请求体、Authorization Header 和上游响应中的敏感字段。
- 不把 AppCode、加密密钥或完整证件信息返回到前端初始化数据。
- 认证接口增加用户级限流和失败重试间隔，防止滥用和重复扣费。
- 上游网络失败、超时和服务商错误不改变用户认证状态。
- 认证成功后只允许管理员重置，不允许用户通过普通资料更新接口覆盖认证字段。

## 10. 数据库与兼容性

实名认证表使用 GORM AutoMigrate，字段使用 SQLite、MySQL 5.7.8+ 和 PostgreSQL 9.6+ 都支持的类型。不得依赖数据库专有 JSON 类型或数据库专有加密函数。

旧用户没有实名认证记录时按“未认证”处理，不需要回填虚假数据。功能开关默认关闭，升级后不改变现有用户和 Key 的行为。

## 11. 验证计划

后端需要覆盖：

- `error_code = 0` 且 `result.isok = true/false` 的判定；
- 企业 `code=10000` 且四个 `*_result` 全为 `1`、任一为 `2`、任一为 `3` 或缺失的判定；
- HTTP 200、400、403、500 等状态和 `10028` 等业务码的处理；
- 企业 `10001/10002/10003/10004/10005` 的处理和 `seqNo` 保存；
- AppCode 未配置、加密密钥未配置、上游超时；
- 认证成功后的加密保存和脱敏返回；
- 普通用户不能读取完整证件信息；
- 管理员查看、审计和重置；
- 强制开关关闭时所有模型/API 服务和三类 Key 创建均保持原行为；
- 强制开关开启时未认证用户的所有模型/API 服务请求均被拦截；
- 强制开关开启时普通 Key、订阅 Key 和注册初始 Key 创建均按策略拦截；
- 强制开关开启时已有 Key 不能调用模型/API 服务；用户完成任一认证后恢复；
- 管理员重置后，现有 Key 的模型/API 调用再次被拦截，资料和认证入口仍可访问；
- 个人或企业认证方式分别启用/禁用时，用户入口和对应 `POST` 接口与配置一致；
- 只配置一种方式时用户只能使用该方式，两种都配置时用户可以二选一；
- 禁用一种方式不会撤销已经成功的对应认证；
- SQLite、MySQL、PostgreSQL 迁移兼容性。

前端需要覆盖认证表单、成功/失败/服务异常提示、开关配置、管理员查看和多语言文案。

## 12. 暂定决策与待确认项

已确认：

- 第一版支持个人二要素核验和企业四要素核验，用户未认证时二选一；
- 个人和企业分别使用独立的 AppCode 配置；
- 个人和企业认证方式分别配置、分别启用；只可用一种时用户只能使用该方式，两种可用时用户二选一；
- `result.isok` 只有 true/false；
- 只有 HTTP 200 + `error_code=0` + `result.isok=true` 才算认证成功；
- 企业只有 HTTP 2xx + `code=10000` + 四个 `*_result` 全为 `1` 才算认证成功；
- HTTP 状态会随业务码返回；
- 实名功能开关与强制实名服务访问开关分离；
- 强制开关默认关闭；
- 管理员需要查看完整姓名和身份证号；
- 证件信息服务端加密保存；
- 企业认证通过后，企业名称、统一社会信用代码/工商注册号和法人/主要人员信息也作为用户实名资料保存；
- 认证成功后用户不能切换认证类型或修改认证资料；
- 强制实名开关开启时，未认证用户除必要账户入口外的所有平台业务服务均不可用，包括已有 Key 发起的模型/API 请求；
- 系统访问令牌不作为业务服务凭据，登录、个人资料和实名认证入口保持可用。
- 认证方式配置只影响后续新认证，不会自动撤销已成功的认证；撤销必须由管理员重置。

暂定、实现前仍需确认：

- 是否需要在第一版保留个人和企业各自的 AppKey/AppSecret 配置字段；
- 身份证格式校验的具体规则和允许的姓名字符范围；
- 企业统一社会信用代码/工商注册号的格式校验规则；
- 企业认证中的“法人/主要人员”是否固定为法定代表人，还是允许服务商定义的主要人员；
- 企业接口参数表中的 `key` 是否必需（参数表与示例请求不一致）；
- 管理员查看完整证件信息是否强制二次安全验证；
- 重置后旧的加密认证资料是否保留为可供管理员查看的历史版本，还是仅保留审计记录；
- 国内站和国际站是否都启用，还是先只在国内站启用。
